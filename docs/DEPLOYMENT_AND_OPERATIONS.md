**این سند چیست:** مرجع انتشار و بهره‌برداری؛ ابتدا وضعیت واقعی امروز روی GitHub Pages، سپس مسیر آیندهٔ Docker روی میزبان ایران، به‌همراه متغیرهای محیطی، پشتیبان‌گیری، پایش و بازگشت.

## ۳. جریان بیلد استاتیک

### گام ۱ — بررسی وضعیت مخزن

```bash
cd franchise-plus-platform
git status
```

**نتیجهٔ مورد انتظار:** شاخهٔ `main` و هیچ تغییر کامیت‌نشده. بیلد از درخت کاری تمیز گرفته می‌شود.

### گام ۲ — نصب قطعی وابستگی‌ها

```bash
npm ci
```

**نتیجهٔ مورد انتظار:** نصب از `package-lock.json` بدون تغییر آن. اگر `package-lock.json` تغییر کرد، یعنی نصب قطعی نبوده و باید بررسی شود.

### گام ۳ — بیلد با مسیر پایه

PowerShell:

```powershell
$env:NEXT_PUBLIC_BASE_PATH = "/franchise-plus"
npm run build
```

bash:

```bash
NEXT_PUBLIC_BASE_PATH=/franchise-plus npm run build
```

**نتیجهٔ مورد انتظار:** پوشهٔ `out/` با این ساختار:

| مسیر در `out/` | محتوا |
|---|---|
| `index.html` | خانه |
| `404.html` | صفحهٔ خطای مسیر ناشناس |
| `opportunities/index.html` و `opportunities/<slug>/index.html` | فهرست و جزئیات |
| `how-it-works/`، `join/`، `dashboard/`، `chat/` | صفحات مربوط |
| `panel/franchisor/`، `panel/admin/` | پنل‌های نمایشی |
| `_next/static/...` | دارایی‌های هش‌دار |

### گام ۴ — بررسی اعمال مسیر پایه

در `out/index.html` عبارت `/franchise-plus/_next/` باید دیده شود.

**نتیجهٔ مورد انتظار:** دست‌کم یک تطابق. اگر مسیرها با `/ _next/` شروع شوند، متغیر محیطی اعمال نشده و انتشار صفحهٔ سفید می‌دهد.

### گام ۵ — پیش‌نمایش محلی

```bash
npx serve out
```

**نتیجهٔ مورد انتظار:** خانه روی پورت پیش‌فرض `serve` باز شود و در تب Network خطای ۴۰۴ نباشد.

**نکته:** اگر بیلد با `NEXT_PUBLIC_BASE_PATH=/franchise-plus` گرفته شده، سرو سادهٔ `out/` در ریشه صفحهٔ سفید می‌دهد؛ چون دارایی‌ها زیر `/franchise-plus/` انتظار می‌روند. برای پیش‌نمایش محلی بدون متغیر بیلد بگیرید یا خروجی را زیر همان زیرمسیر سرو کنید.

### گام ۶ — بررسی محتوا پیش از انتشار

- نوار «پیش‌نمایش طراحی — Phase 1» دیده شود.
- هیچ عدد، برند یا تأییدیهٔ واقعی نباشد.
- لینک شکسته در ۹ مسیر نباشد؛ جزئیات هر فرصت باز شود.
- فونت از دامنهٔ محلی بارگذاری شود، نه CDN.

### خطاهای رایج بیلد

| نشانه | علت | کار |
|---|---|---|
| صفحهٔ سفید در آدرس Pages | بیلد بدون `NEXT_PUBLIC_BASE_PATH` | بیلد دوباره با `/franchise-plus` |
| دارایی ۴۰۴ زیر `_next` | نبود `.nojekyll` در شاخهٔ انتشار | ساخت `.nojekyll` در ریشه و انتشار دوباره |

## ۴. انتشار روی GitHub Pages

**(قطعی، بر اساس گزارش مالک)** منبع Pages در تنظیمات مخزن روی شاخهٔ `gh-pages` است. تغییر این تنظیم فقط با دسترسی مدیریت مخزن و توسط مالک انجام می‌شود.

### ۴.۱ روش جاری: انتشار دستی از snapshot

در محیط فعلی، پوشهٔ کاری انتشار خارج از مخزن اصلی و روی شاخهٔ `gh-pages` قرار دارد؛ در این Workspace با نام `.publish-fp/`. نام پوشه arbitrary است؛ مهم این است که یک clone جداگانه روی شاخهٔ `gh-pages` باشد.

```bash
# ۱) آماده‌سازی clone انتشار (یک‌بار)
git clone --branch gh-pages https://github.com/shimmmmmmmmma/franchise-plus.git ../fp-gh-pages

# ۲) هم‌گام‌سازی با آخرین وضعیت
cd ../fp-gh-pages
git pull --ff-only

# ۳) آینه‌کردن خروجی بیلد (فایل‌های حذف‌شدهٔ بیلد قبلی هم پاک شوند)
rsync -a --delete --exclude '.git' --exclude '.nojekyll' ../franchise-plus-platform/out/ ./

# ۴) اطمینان از وجود نشانگر Jekyll
touch .nojekyll

# ۵) بازبینی و انتشار
git status
git add -A
git commit -m "deploy: phase1 build <short-sha>"
git push origin gh-pages
```

**نکته برای ویندوز:** اگر `rsync` نیست، از ابزار آینه‌سازی مطمئن استفاده کنید؛ شرط اصلی این است که فایل‌های حذف‌شده از بیلد قبلی در شاخه نمانند. پیش از `git add -A` با `git status` بررسی کنید که فقط فایل‌های `out/` دیده شوند.

**نتیجهٔ مورد انتظار:** یک کامیت جدید روی `gh-pages` که درخت آن با `out/` یکسان است و `.nojekyll` در ریشه دارد.

### ۴.۲ بررسی پس از انتشار

1. آدرس `https://shimmmmmmmmma.github.io/franchise-plus/` باز شود؛ نوار پیش‌نمایش دیده شود.
2. سه مسیر تصادفی، از جمله یک جزئیات فرصت، باز شوند.
3. در DevTools، تب Network برای فایل CSS و فونت وضعیت ۲۰۰ نشان دهد.
4. آدرس یک مسیر ناموجود، صفحهٔ ۴۰۴ بدهد.
5. با پنجرهٔ ناشناس و کش خالی تکرار شود؛ اگر نسخهٔ قبلی دیده شد، تا چند دقیقه صبر و دوباره بررسی شود.

**اگر بررسی شکست خورد:** بخش ۹ (بازگشت) اجرا شود؛ انتشار بعدی تا رفع علت انجام نشود.

### ۴.۳ ثبت انتشار

هر انتشار یک رکورد دارد: تاریخ، کامیت `main`، کامیت `gh-pages`، انتشاردهنده، نتیجهٔ بررسی. این رکورد در توضیح PR یا پیام کامیت انتشار نگه داشته می‌شود؛ فایل عملیاتی جداگانه تا تعیین مالکیت ایجاد نشود.

### ۴.۴ انتشار خودکار (پیشنهاد)

**(پیشنهاد)** پس از تأیید مالک، یک workflow در GitHub Actions بیلد را با `NEXT_PUBLIC_BASE_PATH=/franchise-plus` اجرا کند و `out/` را روی Pages منتشر کند؛ یا runner خودمیزبان در صورت محدودیت دسترسی (P-09). شرط‌ها: اجرا فقط از `main`، محیط انتشار با تأیید دستی، و ممنوعیت چاپ متغیرها در لاگ. تا تأیید، روش دستی بخش ۴.۱ معتبر است.

## ۵. مسیر آینده: Docker روی میزبان ایران

**وضعیت:** در انتظار Phase 2 و تأیید مالک. هیچ بخشی از این طرح امروز اجرا نشده و هیچ میزبانی انتخاب یا خریداری نشده است.

### ۵.۱ معماری هدف

| سرویس | نقش | پورت | ماندگاری داده | یادداشت |
|---|---|---|---|---|
| reverse proxy | TLS، مسیردهی، محدودیت نرخ | ۸۰ و ۴۴۳ | فقط تنظیمات | گواهی خودکار یا مدیریت‌شده |
| web | Next.js با رندر سمت سرور و BFF | داخلی ۳۰۰۰ | ندارد | صفحات عمومی و پنل‌ها |
| api | NestJS، مسیر `/api/v1` | داخلی ۳۰۰۱ | ندارد | تنها مسیر دسترسی به دیتابیس |
| postgres | PostgreSQL 16 | داخلی ۵۴۳۲ | volume پایدار | پورت به بیرون منتشر نشود |
| redis | صف یا کش، اختیاری | داخلی ۶۳۷۹ | ندارد | منبع حقیقت نیست |
| object storage | مدارک خصوصی S3-compatible | داخلی یا سرویس بیرونی | bucket خصوصی | URL امضاشدهٔ کوتاه‌عمر |
| worker | پردازش صف و اعلان | — | ندارد | در Phase 6 به بعد |

**قاعدهٔ شبکه:** فقط reverse proxy به اینترنت باز است. دیتابیس، Redis و API از شبکهٔ خصوصی در دسترس‌اند و API تنها راه نوشتن در دیتابیس است.

### ۵.۲ طرح Compose (بدون مقدار حساس)

```yaml
services:
  proxy:
    image: nginx:stable
    ports: ["80:80", "443:443"]
    volumes:
      - ./deploy/nginx.conf:/etc/nginx/nginx.conf:ro
      - ./deploy/certs:/etc/nginx/certs:ro
    depends_on: [web, api]

  web:
    build: ./apps/web
    env_file: .env
    expose: ["3000"]
    depends_on: [api]

  api:
    build: ./apps/api
    env_file: .env
    expose: ["3001"]
    depends_on: [db, redis]

  worker:
    build: ./apps/worker
    env_file: .env
    depends_on: [db, redis]

  db:
    image: postgres:16
    env_file: .env
    volumes: ["db-data:/var/lib/postgresql/data"]
    expose: ["5432"]

  redis:
    image: redis:7
    expose: ["6379"]

volumes:
  db-data:
```

مقادیر از `.env` یا Secret Store میزبان خوانده می‌شوند و در فایل Compose نوشته نمی‌شوند. نام متغیرها در بخش ۶ آمده است. در پیاده‌سازی، دامنهٔ متغیر هر سرویس محدود می‌شود؛ برای نمونه `db` فقط متغیرهای پایگاه‌داده را می‌گیرد. فضای ذخیره‌سازی می‌تواند سرویس بیرونی باشد و در این طرح Compose نیامده است.

### ۵.۳ معیارهای انتخاب میزبان (پیش از خرید)

| معیار | پرسش بررسی | شاهد لازم |
|---|---|---|
| دسترسی از ایران | از چند شبکهٔ ایرانی بدون VPN باز می‌شود؟ | تست از حداقل دو اپراتور |
| محل داده | دیتابیس و مدارک کجا ذخیره می‌شوند؟ | پاسخ کتبی ارائه‌دهنده |
| SLA و پشتیبانی | زمان پاسخ و ساعات پشتیبانی؟ | قرارداد یا صفحهٔ رسمی |
| پشتیبان | snapshot و backup مدیریت‌شده دارد؟ | مستندات و تست بازیابی |
| خروج داده | هزینهٔ egress و امکان خروجی کامل؟ | تعرفه و روش مهاجرت |
| قدرت سخت‌افزار | حداقل ۲ هسته و ۴ گیگ برای web/api و مشابه برای DB کافی است؟ **(فرضیه)** | آزمون بار |
| گواهی TLS | صدور و تمدید خودکار؟ | بررسی فنی |
| پرداخت | امکان پرداخت ریالی و صورتحساب رسمی؟ | رویهٔ فروش |
| ضدحمله | محافظت DDoS و فایروال؟ | مستندات |
| مسیر خروج | اگر ارائه‌دهنده قطع شد، داده چطور منتقل می‌شود؟ | سناریوی مهاجرت |

**الزام:** پیش از خرید، دسترسی واقعی از شبکهٔ ایران و latency سنجیده شود. عدد تبلیغاتی ارائه‌دهنده شاهد نیست.

### ۵.۴ مراحل انتقال آینده

1. ساخت محیط staging روی میزبان تأییدشده، بدون دادهٔ واقعی.
2. اجرای smoke test: health، ورود آزمایشی، بارگذاری مدرک ساختگی.
3. آزمون بازیابی پشتیبان روی همان محیط.
4. تأیید مالک برای دادهٔ واقعی و راه‌اندازی تولید.
5. کاهش TTL رکورد DNS، انتقال، بررسی، سپس افزایش TTL.
6. انتشار عمومی فقط با تأیید جداگانه و پس از چک‌لیست بخش ۱۰.

## ۸. پایش، لاگ و health check

### ۸.۱ وضعیت امروز

- میزبان Pages لاگ سرور در اختیار نمی‌دهد؛ تنها نشانه‌ها وضعیت انتشار و دسترسی مرورگر است.
- هیچ پایش خودکار، هشدار یا uptime check وجود ندارد.
- **(پیشنهاد)** یک پایش بیرونی ساده روی سه آدرس خانه، فهرست فرصت‌ها و یک جزئیات، هر ۵ دقیقه از دو موقعیت جغرافیایی؛ هشدار به کانالی که مالک تعیین می‌کند.

### ۸.۲ نقاط health آینده

| مسیر | چه چیزی را بررسی می‌کند | پاسخ سالم | پاسخ ناسالم |
|---|---|---|---|
| `/health/live` | زنده‌بودن پروسهٔ API | ۲۰۰ بدون وابستگی | timeout یا ۵xx |
| `/health/ready` | اتصال دیتابیس، Redis و دسترسی فضا | ۲۰۰ آماده برای ترافیک | ۵۰۳ با نام اجزای ناسالم، بدون جزئیات حساس |

این دو مسیر طبق بخش ۱۴.۴ `docs/TECHNICAL_ARCHITECTURE.md` تعریف شده‌اند.

**قاعده:** health هرگز رمز، رشتهٔ اتصال، نسخهٔ دقیق کتابخانه یا مسیر داخلی برنگرداند. پاسخ ready برای مصرف‌کنندهٔ بیرونی محدود شود.

### ۸.۳ لاگ

ساختار پیشنهادی هر رکورد: زمان ISO، سطح، نام سرویس، محیط، `request_id`، مسیر، کد وضعیت، مدت میلی‌ثانیه، شناسهٔ شبه‌هویتی کاربر، کد خطا.

**هرگز لاگ نشود:** کد OTP، توکن یا کوکی، شمارهٔ ملی، متن پیام، آدرس مدرک، شمارهٔ کارت، رمز و کلید.

- سطح تولید `info`؛ `debug` فقط در توسعه.
- نگهداشت پیشنهادی ۳۰ روز برای لاگ برنامه و جدا برای ممیزی طبق تصمیم حقوقی.
- لاگ ممیزی از لاگ فنی جدا و فقط‌افزودنی است.

### ۸.۴ هشدارهای پیشنهادی

| نشانه | آستانه **(پیشنهاد)** | اقدام |
|---|---|---|
| نرخ خطای ۵xx | بیش از ۱٪ در ۵ دقیقه | بررسی API و دیتابیس |
| شکست health | ۳ بررسی متوالی | هشدار فوری به اپراتور |
| خطای بیلد یا انتشار | هر مورد | توقف انتشار، بازگشت |
| شکست پشتیبان | هر مورد | اجرای دستی و بررسی علت |
| فضای دیسک | بیش از ۸۰٪ | پاک‌سازی یا افزایش حجم |
| انقضای گواهی TLS | کمتر از ۱۴ روز | تمدید خودکار یا دستی |
| تأخیر صف | بیش از ۵ دقیقه | بررسی worker |

آستانه‌ها پس از دو هفته دادهٔ واقعی بازتنظیم شوند؛ عدد ثابت تبلیغاتی ملاک نیست.

## ۹. رویهٔ بازگشت

### ۹.۱ بازگشت سایت استاتیک

1. کامیت سالم پیش از انتشار معیوب روی `gh-pages` شناسایی شود (`git log --oneline`).
2. کامیت معیوب با یک کامیت جدید جبران شود؛ تاریخچه بازنویسی نشود:

```bash
cd ../fp-gh-pages
git switch gh-pages
git pull --ff-only
git revert --no-commit <bad-deploy-sha>
git commit -m "revert(deploy): restore previous build"
git push origin gh-pages
```

3. وجود `.nojekyll` در ریشه بررسی شود؛ اگر در بازگشت حذف شده بود، دوباره ساخته شود.
4. سه مسیر و یک دارایی CSS بررسی شود؛ کش CDN تا چند دقیقه ممکن است نسخهٔ قبلی را نشان دهد.
5. رکورد حادثه: زمان، علت، کامیت بازگشت، نتیجه.

**نتیجهٔ مورد انتظار:** آدرس عمومی همان محتوای انتشار سالم پیشین را نشان دهد و `git log` یک کامیت بازگشتی داشته باشد، نه حذف تاریخچه.

**اگر علت در کد `main` است:** رفع در شاخهٔ جدا، بیلد تازه و انتشار رو به جلو؛ بازگشت فقط برای توقف خون‌ریزی است.

### ۹.۲ بازگشت در محیط Docker

| وضعیت | اقدام | نکته |
|---|---|---|
| انتشار بد اما مهاجرت بی‌خطر | اجرای تصویر نسخهٔ قبلی با همان متغیرها | تصویر با تگ commit نگه داشته شود |
| انتشار بد همراه مهاجرت مخرب | توقف سرویس، بازیابی پشتیبان، سپس تصویر قبلی | مهاجرت مخرب بدون پشتیبان ممنوع |
| خطای پیکربندی | بازگرداندن فایل تنظیمات قبلی و restart | تغییر را در تاریخچه ثبت کنید |
| خطای گواهی | تمدید یا بازگرداندن گواهی سالم | پایش انقضا |

**سیاست مهاجرت:** فقط رو به جلو و سازگار (الگوی expand/contract). حذف ستون یا تغییر نوع مخرب در همان انتشاری که کد وابسته را حذف می‌کند انجام نشود؛ ابتدا انتشار سازگار، سپس پاک‌سازی در انتشار بعدی.

**نگهداشت تصویر:** دو نسخهٔ آخر با تگ commit و یک تگ `previous` نگه داشته شود. بازگشت بدون بیلد دوباره ممکن باشد.
