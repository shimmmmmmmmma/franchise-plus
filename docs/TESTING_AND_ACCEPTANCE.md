# استراتژی تست و پذیرش فرانچایز پلاس

**این سند چیست:** تعریف عملیِ «آماده» و «تمام‌شده» برای هر فاز پروژه؛ چه چیزی تست می‌شود، با چه معیار قابل اندازه‌گیری، و با چه شاهدی پذیرفته می‌شود. مخاطب آن توسعه‌دهنده، بازبین فنی و مالک محصول است.

**دامنه و پیش‌فرض‌ها:** نسخهٔ فعلی یک پیش‌نمایش استاتیک فارسی/RTL است؛ نه دیتابیس دارد، نه API و نه درگاه پرداخت. معیارهای فازهای ۲ تا ۸ برای معماری خط مبنا (Next.js + NestJS + PostgreSQL + Prisma) نوشته شده‌اند و تا شروع آن فاز، «برنامه» هستند نه «واقعیت».

**نسخه:** ۰.۱ (پیش‌نویس برای تأیید مالک) · **تاریخ:** ۱۴۰۵/۰۹/۰۴

**مبنای بررسی:** `package.json`، `next.config.mjs`، نُه صفحهٔ `app/`، `components/`، `lib/`، و خط مبنای فنی مورد تأیید (بخش‌های ۵، ۷ و ۸).

## ۱. خلاصهٔ اجرایی

در زمان نوشتن این سند، مخزن **هیچ تست خودکاری ندارد**: `package.json` تنها سه اسکریپت `dev`، `build` و `start` را تعریف می‌کند و هیچ وابستگی تست، لینتر یا ابزار دسترس‌پذیری نصب نیست. بنابراین هیچ ادعای «تست شد» دربارهٔ این نسخه معتبر نیست؛ تنها چیزی که می‌توان گفت این است که صفحات و مسیرها در کد وجود دارند و خروجی استاتیک در `next.config.mjs` تنظیم شده است.

این سند سه کار می‌کند:

1. **قاعدهٔ شاهد** را تعریف می‌کند: هر «تمام شد» باید به یک فایل یا خروجی قابل بازکردن وصل باشد، با تاریخ و کد خروج. جملهٔ «اجرا کردم» شاهد نیست.
2. **معیار پذیرش هر فاز** را به عدد و رفتار قابل مشاهده تبدیل می‌کند؛ نه به فهرست آرزو.
3. **تست‌های اجباری پرداخت و دسترسی** را جدا و با جزئیات تعیین می‌کند، چون خطا در این دو حوزه پول و دادهٔ خصوصی را هدف می‌گیرد و با بازبینی چشمی قابل کشف نیست.

نتیجهٔ عملی برای Phase 1: نمونهٔ کد آماده است، اما پذیرش Phase 1 بدون اجرای چک‌لیست‌های بخش ۱۵ و ثبت شواهد در گزارش پیوست، ممکن نیست.

|---|---|
| تست واحد | وجود ندارد؛ Phase 2 |
| تست یکپارچگی | وجود ندارد؛ نیازمند DB و API |

## ۲. وضعیت تصمیم‌ها

## ۳. قاعدهٔ «تمام‌شده فقط با شواهد اجرا»

### ۳.۱ شاهد معتبر چیست

| شاهد | مؤثر برای | شرط اعتبار |
|---|---|---|
| خروجی خام دستور تست با کد خروج ۰ | واحد، یکپارچگی، E2E | تاریخ، نام شاخه و کامیت ثبت شود |
| گزارش CI با پیوند قابل بازکردن | همهٔ سطوح | حداقل ۳۰ روز قابل دسترسی باشد |
| گزارش JUnit/XML یا HTML پوشش | واحد و یکپارچگی | فایل واقعی، نه خلاصهٔ دست‌نویس |
| ویدئو یا اسکرین‌شات Playwright | E2E | نام سناریو و تاریخ در آن دیده شود |
| گزارش axe یا Lighthouse | دسترس‌پذیری و عملکرد | فایل JSON، نه فقط عدد در چت |
| رکورد DB پیش و پس از سناریو | پرداخت، دسترسی، مهاجرت | انتخاب ستون‌های حساس ممنوع |
| گزارش بازیابی پشتیبان | Phase 8 | زمان شروع، پایان و تعداد رکورد |
| امضای مالک در گزارش فاز | پذیرش محصولی | تاریخ و نسخهٔ سند |

### ۳.۲ شاهد نامعتبر

- جملهٔ «تست شد» یا «کار می‌کند» بدون فایل.
- اسکرین‌شات بدون تاریخ، بدون نام سناریو یا از محیط نامعلوم.
- تستِ `skip` شده یا `only` شده که در گزارش سبز دیده می‌شود.
- پوشش کد بدون فایل گزارش، یا پوشش بالا روی کد بی‌ارزش.
- اجرای دستی بدون چک‌لیست مکتوب و بدون نام اجراکننده.
- «روی سیستم من کار کرد» بدون ثبت مرورگر، نسخه و اندازهٔ صفحه.

### ۳.۳ سه سطح ادعا

| سطح | معنا | نحوهٔ بیان در گزارش |
|---|---|---|
| اجرا شد | دستور اجرا و خروجی ثبت شده است | «اجرا شد: `<command>` — کد خروج ۰ — `<artifact>`» |
| مشاهده شد | رفتار در محیط دیده شده اما تست خودکار ندارد | «مشاهده شد: `<سناریو>` در `<مرورگر>` — شاهد: `<فایل>`» |
| ادعا | هنوز بررسی نشده | «بررسی نشده» یا «در انتظار Phase X» |

### ۳.۴ ضدالگوهای ممنوع

1. بستن فاز با نقص باز سطح A.
2. نوشتن تست برای رد کردن گیت، بدون assertion واقعی.
3. mock کردن کل مسیر پرداخت و نتیجه‌گیری «پرداخت تست شد».
4. استفاده از دادهٔ واقعی برای «واقعی‌تر شدن تست».
5. ثبت رمز یا توکن در لاگ تست یا اسکرین‌شات.
6. اعلام پذیرش بدون امضای مالک در فازهایی که گیت محصولی دارند.
7. تغییر معیار پذیرش پس از شکست تست، بدون ثبت در همین سند و تأیید.

## ۴. هرم تست و ابزارها

| سطح | هدف | ابزار پیشنهادی | سهم پیشنهادی | اجرا در |
|---|---|---|---|---|
| واحد | منطق خالص: پول، ارقام، قواعد تطبیق، مجوز | Vitest | ۶۰٪ | هر کامیت |
| یکپارچگی | API + DB + تراکنش + ممیزی | Vitest + Testcontainers یا Postgres موقت | ۲۵٪ | هر PR |
| سرتاسری | مسیرهای بحرانی کاربر | Playwright | ۱۵٪ | هر PR و پیش از انتشار |
| دسترس‌پذیری | نقض خودکار | axe-core در Playwright | مکمل | هر PR |
| عملکرد | بودجهٔ Core Web Vitals | Lighthouse CI | مکمل | هر PR به `main` |

**نکتهٔ مهم:** این ابزارها امروز نصب نیستند. افزودن آن‌ها، تعریف اسکریپت‌ها و اجرای اولین مجموعهٔ سبز، بخشی از پذیرش Phase 2 است — نه کاری که انجام شده فرض شود.

قاعدهٔ انتخاب ابزار: هر ابزاری که به سرویس بیرونی وابسته است باید در CI قابل mock یا sandbox باشد. تستی که فقط روی ماشین توسعه‌دهنده اجرا می‌شود، شاهد نیست.

## ۵. تست واحد

### ۵.۱ دامنهٔ الزامی

| ماژول | چه چیزی تست می‌شود | حالت‌های مرزی |
|---|---|---|
| پول | تبدیل ریال/تومان، جمع، مقایسه، قالب‌بندی | صفر، منفی، سرریز، اعشار ممنوع |
| ارقام فارسی | `faNum` و رفت‌وبرگشت | رشتهٔ خالی، رقم لاتین مخلوط، نویسهٔ غیررقم |
| قواعد تطبیق | نسخه‌دار و قابل توضیح | نبود بودجه، منطقهٔ خارج از فهرست، صنعت ناشناخته |
| ماشین وضعیت پرونده | گذارهای مجاز و ممنوع | پرش از مرحله، بازگشت، وضعیت تکراری |
| مجوز | تابع تصمیم دسترسی | نقش درست با پروندهٔ اشتباه، نقش اشتباه با پروندهٔ درست |
| اعتبارسنجی فرم | تلفن، نام، بودجه | فاصله، ارقام فارسی، ورودی خالی |
| وضعیت پرداخت | نگاشت وضعیت درگاه به وضعیت داخلی | وضعیت ناشناخته، وضعیت خالی |

### ۵.۲ قواعد

- تست واحد به DB، شبکه و ساعت واقعی وابسته نیست؛ زمان و شناسه تزریق می‌شوند.
- هر تست یک رفتار را می‌سنجد و نام آن رفتار را می‌گوید، نه نام تابع را.
- تست پول هرگز از `float` استفاده نمی‌کند؛ ورودی و انتظار، عدد صحیح با واحد روشن است.
- تست مجوز باید حالت «رد» را هم بسنجد؛ تستی که فقط اجازه را بررسی می‌کند، نشت را نمی‌گیرد.

نمونهٔ جهت‌نما (نام‌ها انگلیسی، طبق قاعدهٔ کد؛ متن‌ها فارسی):

```ts
// مبلغ‌ها در DB به ریال و عدد صحیح ذخیره می‌شوند.
it('مبلغ فاکتور با پرداخت ناهم‌خوان را رد می‌کند', () => {
  const invoice = { amountRial: 25_000_000, status: 'open' as const };
  const result = reconcilePayment(invoice, { amountRial: 24_000_000 });
  expect(result.ok).toBe(false);
  expect(result.reason).toBe('AMOUNT_MISMATCH');
  expect(result.invoiceStatus).toBe('open');
});
```

### ۵.۳ معیار خروج

- پوشش خط ≥ ۸۰٪ در ماژول‌های دامنه و ۱۰۰٪ در `money`، `permissions` و `payment-state`.
- صفر تست `skip` در مجموعهٔ اصلی.
- زمان اجرای مجموعهٔ واحد زیر ۶۰ ثانیه در CI (پیشنهاد).

## ۶. تست یکپارچگی

### ۶.۱ دامنه

- مهاجرت‌ها: `up` روی DB خالی، `down` و بازگشت دوباره، بدون دادهٔ یتیم.
- تراکنش: ثبت پرداخت و اثر مالی در یک تراکنش؛ شکست میانهٔ کار نباید رکورد نیمه‌کاره بسازد.
- idempotency: همان کلید دوبار ارسال شود، یک اثر مالی.
- مجوز در سطح API: همان ماتریس بخش ۱۴، این بار روی endpoint واقعی.
- ممیزی: هر مشاهده/تغییر حساس یک رکورد `audit_events` می‌سازد.
- صف و اعلان: رخداد در `outbox_events` ثبت و مصرف می‌شود؛ شکست مصرف، پیام را گم نمی‌کند.
- فایل خصوصی: لینک عمومی وجود ندارد؛ URL امضاشده منقضی می‌شود.

### ۶.۲ معیار خروج

- هر تست روی DB تازه اجرا و پس از خود پاکسازی می‌کند.
- هیچ تستی به ترتیب اجرا وابسته نیست؛ اجرای تصادفی هم سبز است.
- صفر تستی که با `sleep` ثابت منتظر بماند؛ انتظار شرطی است.
- خروجی migration در گزارش CI ذخیره می‌شود.

## ۷. تست سرتاسری (E2E)

### ۷.۱ مسیرهای بحرانی

| شناسه | مسیر | نتیجهٔ قابل مشاهده |
|---|---|---|
| E2E-01 | ثبت‌نام گیرنده، تأیید شماره با OTP mock، تکمیل پرونده | ورود به پنل با وضعیت «پرونده ناقص» و اقدام بعدی مشخص |
| E2E-02 | بارگذاری مدرک و انتظار تأیید | مدرک در پرونده دیده می‌شود؛ وضعیت «در انتظار بررسی» |
| E2E-03 | ارسال درخواست همکاری برای فرصت منتشرشده | درخواست در پنل گیرنده و صف مدیر دیده می‌شود |
| E2E-04 | پذیرش درخواست توسط تیم | گفت‌وگو باز می‌شود؛ پیش از پذیرش لینک گفت‌وگو وجود ندارد |
| E2E-05 | ارسال پیشنهاد برند توسط واگذارکننده | پیشنهاد در صف مدیر؛ هیچ کنش انتشار در پنل واگذارکننده نیست |
| E2E-06 | ساخت و انتشار فرصت توسط Admin | فرصت در فهرست عمومی دیده می‌شود؛ پیش‌نویس دیده نمی‌شود |
| E2E-07 | پرداخت موفق در sandbox | فاکتور «پرداخت‌شده» و دقیقاً یک اثر مالی |
| E2E-08 | بازگشت از درگاه بدون verify | فاکتور هنوز «باز» است؛ دسترسی فعال نمی‌شود |
| E2E-09 | ورود با نقش اشتباه به مسیر پنل دیگر | رد دسترسی، بدون افشای وجود پرونده |
| E2E-10 | چرخهٔ گفت‌وگو: پیام، پیام سیستمی، خروج و ورود دوباره | تاریخچه حفظ می‌شود؛ پیام جدید برای صفحه‌خوان اعلام می‌شود |

### ۷.۲ قواعد

- هر سناریو دادهٔ خودش را می‌سازد و پاک می‌کند؛ وابستگی بین سناریوها ممنوع.
- انتخابگرها مبتنی بر نقش و برچسب فارسی‌اند (`getByRole`, `getByLabel`)، نه کلاس CSS.
- هر سناریو در دو اندازهٔ ۳۹۰px و ۱۴۴۰px اجرا می‌شود؛ حداقل یک سناریو در ۳۶۰px.
- ویدئو و trace برای هر شکست ذخیره می‌شود.

## ۸. تست امنیت

این بخش فقط آزمون دفاعی و کنترل دسترسی است؛ هیچ تست نفوذ یا حملهٔ واقعی بدون اجازهٔ کتبی مالک انجام نمی‌شود.

| حوزه | چه چیزی سنجیده می‌شود | معیار قبولی | شاهد |
|---|---|---|---|
| نشست | کوکی امن، `HttpOnly`، `SameSite`، ابطال در خروج | هیچ توکن نشستی در `localStorage` نیست | تست E2E + بازرسی هدر |
| احراز هویت | محدودیت نرخ OTP، انقضای کد، تلاش دوباره | نرخ و انقضا مطابق تنظیم مصوب؛ پیام یکسان برای کاربر ناشناس | تست یکپارچگی |

هدف پیشنهادی: WCAG 2.2 سطح AA. معیار قبولی خودکار: صفر نقض `critical` و `serious` در axe روی هر صفحهٔ اصلی.

### ۹.۲ آزمون دستی صفحه‌کلید

1. از بالای صفحه با Tab شروع کن؛ اولین فوکوس باید پیوند پرش باشد و دیده شود.
2. تا انتهای صفحه پیش برو؛ هیچ عنصر تعاملی نباید بدون فوکوس قابل مشاهده باشد.
3. در پنل، ناوبری کنار و جدول باید با Tab و Enter قابل استفاده باشند.
4. در گفت‌وگو، ارسال با Enter و بدون ماوس ممکن باشد.
5. با Shift+Tab برگرد؛ ترتیب معکوس درست باشد.

### ۹.۳ صفحه‌خوان

حداقل یک آزمون دودی با NVDA روی ویندوز و یک آزمون با TalkBack روی اندروید: خواندن تیترها، برچسب فرم، خطای فرم، بج وضعیت و پیام جدید گفت‌وگو. شاهد: فهرست موارد خوانده‌شده و مشکل‌ها.

| شناسه | چه چیزی | روش | معیار قبولی |

هر نتیجه باید در فهرست استثناهای سند طراحی باشد؛ نتیجهٔ جدید یعنی نقض.

## ۱۳. تست‌های اجباری پرداخت

این بخش بدون توجه به انتخاب میزبان یا نسخهٔ زرین‌پال معتبر است. هیچ قیمت، درصد یا سیاست استردادی در این تست‌ها فرض نمی‌شود؛ مبلغ از فاکتور ساخته‌شده در همان تست می‌آید.

### ۱۳.۱ پنج قاعدهٔ طلایی

1. فاکتور فقط از دادهٔ سمت سرور ساخته می‌شود؛ مبلغ از کلاینت پذیرفته نمی‌شود.
2. callback مرورگر ورودی نامطمئن است؛ تأیید فقط با verify سمت سرور.
3. مبلغ و مرجع درگاه با فاکتور داخلی تطبیق داده می‌شود.
4. ثبت نتیجه با کلید idempotency و قید یکتایی در DB انجام می‌شود.
5. هیچ دسترسی، اشتراک یا امتیازی پیش از ثبت «پرداخت‌شده» فعال نمی‌شود.

### ۱۳.۲ سناریوهای اجباری

| شناسه | Given | When | Then (قابل اندازه‌گیری) |
|---|---|---|---|
| PAY-01 | فاکتور باز با مبلغ مشخص | پرداخت موفق و verify معتبر | یک `payment_attempt` با وضعیت `paid`؛ جمع اثر مالی برابر مبلغ فاکتور؛ فاکتور `paid`؛ یک رکورد ممیزی |
| PAY-02 | پرداخت موفق PAY-01 | همان callback دوباره ارسال می‌شود | پاسخ موفق idempotent؛ **هیچ** رکورد مالی دوم؛ مبلغ کل تغییر نمی‌کند |
| PAY-03 | دو callback هم‌زمان با یک authority | هر دو در یک بازهٔ کوتاه پردازش می‌شوند | قید یکتایی یکی را می‌پذیرد؛ دیگری نتیجهٔ همان تراکنش را برمی‌گرداند؛ صفر خطای ۵۰۰ |
| PAY-04 | فاکتور ۱۰۰ واحد | callback مبلغ ۹۰ یا ۱۱۰ واحد | وضعیت `mismatch`؛ فاکتور باز می‌ماند؛ صفر اثر مالی `paid`؛ یک `reconciliation_case` |
| PAY-05 | فاکتور باز | verify پاسخ ناموفق می‌دهد | وضعیت `failed`؛ فاکتور باز؛ دسترسی فعال نمی‌شود؛ پیام کاربر بدون افشای جزئیات فنی |
| PAY-06 | کاربر از درگاه بازگشته | هیچ verify سمت سرور اجرا نشده | فاکتور همچنان `open`؛ صفحهٔ نتیجه نمی‌گوید «پرداخت موفق» |
| PAY-07 | authority متعلق به فاکتور کاربر دیگر | درخواست با نشست کاربر دوم | رد ۴۰۳/۴۰۴؛ صفر تغییر وضعیت؛ رکورد تلاش ناموفق |
| PAY-08 | درگاه timeout می‌دهد | درخواست دوباره ارسال می‌شود | حداکثر یک اثر مالی؛ تلاش دوم به همان نتیجه می‌رسد |
| PAY-09 | callback با پارامتر ناقص یا امضای نامعتبر | پردازش می‌شود | رد قبل از هر نوشتن؛ صفر تغییر DB؛ لاگ بدون دادهٔ حساس |
| PAY-10 | فاکتور قبلاً پرداخت شده | تلاش پرداخت جدید آغاز می‌شود | تلاش جدید ساخته نمی‌شود یا بلافاصله بسته می‌شود؛ پیام «قبلاً پرداخت شده» |
| PAY-11 | سیاست استرداد تصویب شده | استرداد کامل ثبت می‌شود | اثر مالی معکوس با کلید یکتا؛ جمع نهایی صفر؛ ممیزی کامل |
| PAY-12 | مغایرت باز | کارشناس مالی آن را می‌بندد | وضعیت مغایرت بسته؛ دلیل اجباری؛ اثر مالی فقط با تأیید مجاز |

### ۱۳.۳ قواعد داده و محیط

- تمام تست‌ها با sandbox یا mock درگاه اجرا می‌شوند؛ هیچ اتصال زنده در CI.
- کلید درگاه فقط در مخزن اسرار محیط تست است؛ در گزارش و ویدئو ماسک می‌شود.
- هر تست، فاکتور خودش را می‌سازد و مبلغ را از همان فاکتور می‌خواند.
- تست پرداخت با دادهٔ ساختگی و کاربر ساختگی اجرا می‌شود.

### ۱۳.۴ شاهد لازم برای بستن Phase 7

گزارش اجرای ۱۲ سناریو، خروجی SQL قبل و بعد از PAY-02 و PAY-03 (تعداد رکورد و جمع مبلغ)، و تأیید کتبی مالک بر قیمت‌ها و سیاست استرداد. بدون این سه، Phase 7 بسته نمی‌شود.

### ۱۵.۱ جزئیات گیت Phase 1

1. `npm run build` بدون خطا و با تولید هر ۹ مسیر تمام شود؛ خروجی مسیرها در گزارش ثبت شود.
2. در ۳۶۰، ۷۶۸ و ۱۴۴۰ پیکسل، هیچ صفحه‌ای اسکرول افقی نداشته باشد.
3. هر صفحه دقیقاً یک `h1` داشته باشد و سلسله‌مراتب تیتر نشکند.
4. همهٔ کنترل‌های تعاملی حداقل ۴۴×۴۴px باشند؛ سه استثنای شناخته‌شده (چیپ، دکمهٔ کوچک، پیوند فوتر) باید اصلاح شوند.
5. نسبت کنتراست متن عادی ≥ ۴٫۵:۱ باشد؛ `--muted-2` برای متن استفاده نشود.
6. پیوند پرش با اولین Tab دیده شود.
7. فرم ثبت‌نام: خطای فیلد، حفظ مقدار و ادامهٔ مسیر درست کار کند.
8. فهرست فرصت‌ها: حالت خالی واقعی و بازگشت فیلتر کار کند.
9. بازبینی مالک: هر یک از هشت اصل با «قبول / نیازمند اصلاح» و توضیح یک‌خطی ثبت شود.
10. هیچ دادهٔ واقعی، رمز یا اطلاعات بانکی در مخزن و شواهد نباشد.
11. مسیر «خانه → فهرست → جزئیات → ثبت‌نام → پنل → درخواست → گفت‌وگو» بدون بن‌بست قابل دنبال‌کردن باشد.
12. برای هر صفحهٔ داده‌محور، چهار حالت خالی/بارگذاری/خطا/موفقیت در سند طراحی تعریف شده باشد؛ این بند «تعریف» را می‌سنجد، نه ادعای پیاده‌سازی.
13. ماتریس دسترسی، دادهٔ ممنوعهٔ هر نقش را صریح نام ببرد؛ نه فقط دادهٔ مجاز (مرجع: `docs/SECURITY_AND_ACCESS_CONTROL.md`، پس از تدوین).

## ۱۷. دادهٔ تست و محیط‌ها

| محیط | داده | درگاه | دسترسی |
|---|---|---|---|
| محلی | seed ساختگی، بازنشانی در هر اجرا | mock | توسعه‌دهنده |
| CI | همان seed، DB موقت | mock | خودکار |
| Staging | ساختگی، شبیه تولید | sandbox | تیم |
| Production | واقعی | live | فقط پس از تأیید انتشار |

قواعد:

- هیچ دادهٔ هویتی واقعی، شمارهٔ ملی، کارت بانکی یا مدرک واقعی در هیچ محیط تستی بارگذاری نمی‌شود.
- نام‌ها و برندهای تست از `lib/data.ts` یا seed ساختگی می‌آیند و در صورت نیاز با پیشوند «نمونه» مشخص می‌شوند.
- `.env.example` فقط نام متغیرها را دارد؛ مقدار واقعی در مخزن اسرار محیط است.
- دادهٔ تست پس از اجرا پاک می‌شود؛ تستی که به دادهٔ باقی‌مانده وابسته است، معتبر نیست.
