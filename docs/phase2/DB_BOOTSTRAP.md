# Phase 2 — گام اول: زیربنای دیتابیس

**وضعیت:** foundation محلی و محدود Phase 2؛ پذیرش مالک Phase 1 در `docs/phase1/ACCEPTANCE_RECORD.md` بر مبنای commit `4002c70fef15ff9662e0db9e3356b44a12f48f3a` ثبت شده است. این پذیرش به‌معنای تکمیل یا پذیرش فنی Phase 2 نیست؛ API و احراز واقعی هنوز پیاده/آزموده نشده‌اند.<br>
**دامنه:** PostgreSQL محلی، Prisma، migration پایه، نقش‌های آغازین و طبقه‌بندی نمونهٔ توسعه.<br>
**تاریخ نگارش نسخهٔ نخست:** ۱۴۰۵/۰۸/۳۰ (۲۰۲۶-۱۱-۲۱؛ تاریخ گزارش اولیه، نه تاریخ commit)

## تصمیم‌های این برش

- پایگاه‌دادهٔ هدف PostgreSQL است؛ نسخهٔ محلی این برش PostgreSQL 17 است، سازگار با حداقل نسخهٔ 16 در `DATABASE_SCHEMA.md`.
- Prisma با نسخهٔ تثبیت‌شدهٔ 6.19.3 به‌کار می‌رود تا شکل `schema.prisma` با سند موجود سازگار بماند.
- پیش‌نمایش Next.js همچنان static export است. در این برش API، ورود واقعی، دادهٔ واقعی یا استقرار backend اضافه نمی‌شود؛ GitHub Pages میزبان API/DB نیست.
- مدل فعلی فقط این هفت جدول را دارد: `users`, `roles`, `user_roles`, `sessions`, `otp_challenges`, `audit_events`, `industries`. جدول‌های دیگر `DATABASE_SCHEMA.md` در migrationهای افزایشی بعدی می‌آیند.
- فقط پنج نقش خواسته‌شدهٔ مالک در seed توسعه هستند: `APPLICANT`, `FRANCHISOR`, `VERIFICATION_OFFICER`, `ADMIN`, `SUPER_ADMIN`. هیچ نقش دیگری بی‌صدا اضافه یا seed نمی‌شود. حساب کاربری یا Super Admin پیش‌فرض نیز ساخته نمی‌شود.
- مالک چندنقشی بودن حساب را تأیید کرده است؛ احراز هر نقش مستقل است، `active_role` باید صریح و سمت سرور اعتبارسنجی شود، و تعارض Applicant/Franchisor در همان پرونده به کارشناس دیگری تخصیص یافته و در audit ثبت می‌شود. این‌ها قواعد مصوب‌اند، نه ادعای enforcement؛ API-level enforcement هنوز پیاده/آزموده نشده است.
- دسته‌های صنعت seed از فهرست نمایشی فعلی گرفته شده‌اند و فقط دادهٔ توسعه‌اند؛ انتخاب صنایع پایلوت یا محتوای عمومی محسوب نمی‌شوند.
- seed پیش از هر اتصال، میزبان loopback و نام پایگاه‌داده با پسوند `_dev` یا `_test` را بررسی می‌کند و در production رد می‌شود.
- رویداد ممیزی فقط‌افزودنی است: `UPDATE`/`DELETE`/`TRUNCATE` مستقیم رد می‌شود. برای هم‌خوانی با `DATABASE_SCHEMA.md`، هنگام حذف فیزیکی کاربر، کلید خارجی `actor_user_id` می‌تواند به‌صورت داخلی `SET NULL` شود؛ سایر فیلدهای رویداد و snapshot نقش تغییر نمی‌کنند. حذف رویداد همچنان رد می‌شود.
- migration این برش runtime DB role نمی‌سازد؛ پیش از runtime واقعی باید کاربر برنامهٔ غیرمالک جداگانه با حداقل مجوزهای لازم (از جمله فقط `SELECT` و `INSERT` روی ممیزی) ساخته شود. اجرای اپ با مالک migration یا superuser الگوی production نیست. در image رسمی Compose، `POSTGRES_USER` کاربر bootstrap با دسترسی superuser می‌سازد؛ آن را فقط برای توسعهٔ محلی نگه دارید.
- trigger مانع دستکاری توسط superuser یا مدیر زیرساخت نیست. زنجیرهٔ رمزنگاری و لنگر بیرونی/WORM در این برش پیاده نشده و نباید «ضد دستکاری مطلق» ادعا شود.

## راه‌اندازی محلی

### گزینهٔ A: Docker Compose

1. `cp .env.example .env` را اجرا کنید و فقط در `.env` محلی مقدارهای DB را تنظیم کنید. `.env` در `.gitignore` است و نباید commit شود؛ template مقادیر گذرواژه و URL را خالی می‌گذارد.
2. یک گذرواژهٔ تصادفی محلی را فقط در `.env` قرار دهید و `DATABASE_URL` را با همان مقدار تنظیم کنید. Compose از `${POSTGRES_PASSWORD:?...}` استفاده می‌کند و در صورت unset یا خالی بودن متغیر خطا می‌دهد؛ مقدار واقعی را در Git یا log ننویسید. پورت پیش‌فرض Compose برابر 5433 است.
3. پایگاه‌داده را بالا بیاورید: `docker compose -f compose.dev.yml up -d db`.
4. وابستگی‌ها و Prisma را آماده کنید: `npm ci`.
5. اعتبارسنجی و migration را اجرا کنید: `npm run db:validate` سپس `npm run db:migrate:dev`.
6. seed توسعه را اجرا کنید: `npm run db:seed`.
7. وضعیت را بازبینی کنید: `npm run db:status`.

Compose فقط روی `127.0.0.1:5433` bind می‌شود و پورت دیتابیس را روی شبکهٔ عمومی منتشر نمی‌کند. پورت 5433 برای جلوگیری از تداخل با PostgreSQL میزبان است. فایل Compose در این محیط اجرا نشده است، چون Docker نصب نیست؛ گزینهٔ PostgreSQL سیستمی در ادامه آزموده شده است.

### گزینهٔ B: PostgreSQL نصب‌شده

PostgreSQL 16 یا بالاتر را محلی اجرا کنید و یک DB با پسوند `_dev` بسازید. نقش توسعه باید برای `prisma migrate dev` امکان ساخت shadow database داشته باشد؛ این اجرای محلی از `fp_dev` با `CREATEDB` استفاده کرد، نه از یک نقش runtime. سپس `DATABASE_URL` را در `.env` محلی تنظیم کنید (نمونه‌پورت سرور میزبان 5432 است؛ Compose از 5433 استفاده می‌کند) و مراحل ۴ تا ۷ بالا را اجرا کنید. این برش در محیط مجری با PostgreSQL 17.12 رسمی Debian آزموده شده است؛ سرویس و DB آن محلی‌اند و هیچ داده‌ای به GitHub Pages یا میزبان عمومی ارسال نشده است.

## محتوای seed

- پنج رکورد نقش آغازین، با شناسهٔ پایدار `code`.
- هفت طبقهٔ نمونهٔ صنعت از پیش‌نمایش Phase 1، بدون «همه» که فقط گزینهٔ فیلتر UI است.
- صفر کاربر، شمارهٔ تلفن، رمز، OTP، فرصت یا تراکنش.
- اجرای دوباره با `upsert` انجام می‌شود و رکورد تکراری نمی‌سازد.

## مرزهای باز

- انتخاب نام نقش‌های API و نگاشت آن‌ها به نام‌های قدیمی‌تر `DATABASE_SCHEMA.md`/`API_SPECIFICATION.md` فقط در حد پنج نقش آغازین ثبت شده؛ نقش‌های دیگر در این مرحله seed نمی‌شوند.
- تصمیم چندنقشی، احراز مستقل، active role و تعارض same-case از سوی مالک بسته شده است؛ پیوند فیزیکی پروندهٔ احراز به `user_roles` و enforcement/API test هنوز نیازمند طراحی، پیاده‌سازی و پذیرش فنی‌اند.
- روش امن و قابل بازیابی برای ایجاد اولین حساب SuperAdmin هنوز تصمیم و پیاده‌سازی نشده است؛ credential پیش‌فرض یا حساب seed ممنوع است.
- migration کامل مدل بلندمدت هنوز انجام نشده؛ جدول‌های ماژول‌های بعدی باید با migrationهای جدا و بازبینی‌شده اضافه شوند.
- میزبان، پیامک، فضای فایل و CI انتخاب نشده‌اند. هیچ استقرار یا خریدی در این مرحله مجاز/انجام‌شده تلقی نمی‌شود.

آزمون‌ها فقط بر DBهای محلی `_dev` و `_test` انجام شدند. API، runtime DB role کم‌دسترسی، استقرار و معیارهای پذیرش Phase 1/2 در این برش پیاده یا پذیرفته نشده‌اند.
